# Обращения SY3 в собственном Битрикс24

Владелец24.10.2026 разрешил сохранять обращения в `https://sy3.bitrix24.ru/`. Включён простой режим CRM (`crm.settings.mode.get=2`), поэтому используются контакты и сделки, без переключения режима. Существующая воронка8 «Квалификация», стадия `C8:NEW` «Входящие», ответственный — владелец1. Тариф/оплаты, стадии и роботы этой интеграцией не меняются.

## Поток данных

Существующая `sy3-leads.timer` продолжает запускать одного root worker. Сначала он доставляет подтверждённые уведомления в Telegram/MAX, затем отдельным модулем `delivery/crm_bridge.py` сохраняет CRM. Расписание не меняется; общий timeout службы увеличен с90 до180секунд для двух ограниченных75секундами этапов. Секретный incoming webhook только scopeCRM хранится в `/root/.config/client-access/sy3.ru/bitrix24-rest.json`, root0600, вне WordPress и Git. Домен, владелец, воронка и стадия строго ограничены кодом. HTTP redirects и proxy из environment не используются; TLS проверяется.

Формы читаются из существующей очереди, с прежней проверкой владельца/permissions/схемы. Public inbox Telegram/MAX читаются через SQLite `mode=ro` и `query_only`, без копирования БД и изменений schema1, ботов, их флагов/pins или webhook. Новые обращения ограничены фиксированным `cutoff`; старые тестовые записи не импортируются. У каждого бота свой устойчивый курсор. Источник, страница, UTM, задача и доступная Telegram-ссылка сохраняются в CRM. Для MAX ссылка на профиль не выдумывается; номер исходного обращения позволяет восстановить привязку в штатном inbox.

Контакт ищется по собственному внешнему идентификатору, а для формы также по телефону/email. При нескольких совпадениях автоматического объединения нет. Новое сообщение к тому же контакту добавляется комментарием в единственную открытую сделку этой воронки. Закрытая сделка не открывается заново; при отсутствии открытой создаётся новая. Существующие контактные данные/стадии/описание сделки не переписываются. Несколько открытых сделок требуют ручного выбора.

## Повторы и неизвестный результат

Перед созданием контакта/сделки записывается отдельная durable reservation по человеку. `originatorId=SY3_WEBSITE` и детерминированный `originId` позволяют найти объект после потерянного ответа, без повторного POST. Для комментария сначала сохраняется точное pending-состояние; после сбоя читается таймлайн сохранённого deal_id и ищется исходный комментарий до выбора другой сделки, даже если прежнюю закрыли или перенесли. Некорректный ответ поиска дублей останавливает запись. Неподтверждённая запись не отправляется вслепую повторно. Reservation человека также останавливает дубли при следующем сообщении того же посетителя.

Локальные sidecars `state/crm-job-*.json` и `crm-person-*.json` содержат статусы, fingerprint и CRM ID, без текста/контакта/webhook. Их пишет root, WordPress читает статус и ссылку на сделку в закрытом разделе заявок. Telegram/MAX состояния не меняются. `retry` означает безопасно отклонённый запрос/лимит; `uncertain` — нужна сверка по существующим внешним ID/таймлайну; `failed` — отказ или неоднозначный выбор, без автоматического объединения. Не редактировать эти состояния ради слепого resend. Неизвестное сообщение бота удерживает курсор его CRM-экспорта; штатная переписка бота при этом работает независимо.

Форма и страница `/privacy/` объясняют фактическое сохранение в Битрикс24. Текст формы/контакт не передаются в цели Метрики. Сам модуль не отправляет сообщений клиенту, не создаёт рассылок, не меняет роботов CRM и не меняет Bridge-права посетителя. Настройки существующих роботов портала остаются отдельной ответственностью CRM.

## Проверка и доставка

`python3 -B -m unittest discover -s wordpress/delivery -p 'test_*.py'`: 54 теста, включая 15 CRM-сценариев и регрессии закрытой/перенесённой сделки после потерянного ответа, альтернативной открытой сделки и некорректных API-ответов. Проверяются replay, существующая/закрытая сделка, потерянные ответы создания/комментария, запрет слепого повтора, неоднозначный контакт, bot cursor/cutoff/read-only источник и HTML-экранирование. Тесты не используют реальные кабинеты/секреты/сообщения.

`tools/install-crm-delivery.py --check/--apply` требует clean exact reviewed HEAD, `SY3_CRM_ALLOW_PRODUCTION=1`, `SY3_CRM_REVIEWED_HEAD`, `SY3_CRM_LOCK_PID` с тремя общими project locks. Четыре точных runtime файла проверяются против принятого before25ccc3c или собственного after; worker lock исключает частичное обновление. Только `sy3-leads.service` получает daemon-reload; новые units/расписания не создаются. Прежний код восстанавливается из опубликованного Git, backup не создаётся.

Перед apply выполнить dry-run узкого `update-lead-privacy.php`: прежняя страница7 байтово совпала с опубликованной фабрикой, SHA256 `fecda708968de507c6a45f9a38e6baeba0eb4404580d5a214f937d49e63d37ae`; редакторские изменения не заменяются. Затем scoped privacy update и installer. Живая приёмка — одна явно техническая заявка через форму, CRM contact/deal read-back, оба bot receipts, тот же повторный request без нового job/deal и принятая JS-цель. Public bot→CRM не считать естественно проверенным, пока реальный другой аккаунт не создаст новое обращение после cutoff.

## Статус публикации 24.10.2026

PR87 принят после независимого PASS exact `3844f4e79e1c4eb758c4f53dcdba85931e16a3df`, merge `ffde487d06381dd69426a267d4ccb202d01f9f56`. Четыре runtime-файла установлены и сверены по SHA256, privacy обновлена узким guarded updater; service успешен, timeout180 секунд, прежний таймер активен. Backup не создавался.

Техническая форма `SY3-94FCAD79863E` создала ровно контакт6 и сделку12 в воронке8/`C8:NEW`, владелец1. Внешние ID, поля и текст прочитаны обратно. Повтор HTTP вернул тот же reference, повторный worker новых уведомлений не отправил; всего2formjobs, включая прежнюю утреннюю проверку. Цель `sy3_lead_accepted` сработала один раз, watch HTTP200. MAX подтвердил уведомление. Telegram: `uncertain/network_unknown`, подтверждение фактического получения запрошено у владельца, повтор не выполняется. Это ограничение transport acknowledgement, а не повод менять state в `sent` вручную.

После cutoff в public bot DB на момент проверки новых диалогов0. Экспорт Telegram/MAX установлен, но естественный bot→CRM roundtrip ещё не подтверждён. Нужен новый внешний диалог; тестовые owner/visitor updates не подделываются. Подробные receipts хранятся вне Git: `private/crm-leads-rollout-20261024.json` и `private/conversion-goals-rollout-20261024.json`.

## Следующий процесс — предложение, не активировано

1. «Входящие»: сохранить заявку и источник, показать контакт/диалог.
2. «Первый контакт»: после личного ответа зафиксировать следующий шаг и срок.
3. «Второй контакт»: если ответа нет, напомнить владельцу; сообщение клиенту сначала показать черновиком с подтверждением.
4. Прекратить напоминания после ответа клиента, отказа, закрытия сделки или выбора другого срока.

Для согласования остаются срок повторного контакта, текст сообщения и канал. Подписка на бота сама по себе не является решением запустить этот процесс. Эта версия не запускает догоняющие сообщения автоматически.
