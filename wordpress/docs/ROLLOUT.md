# Публикация и сохранение адресов

## Текущий статус и authority

Владелец поручил обновить оба сайта на WordPress с фокусом на CRM, интеграции и ИИ. Исходники и локальные установки подготовлены. Точное разрешение на production-переключение доменов, Nginx и создание рабочих баз пока не получено. DNS, боевые каталоги, службы и рабочие базы не менялись. Наличие этого документа не разрешает запуск операций.

## Точные исходные объекты

| Объект | Обнаруженное состояние |
| --- | --- |
| `sy3.ru` | Статические HTML/CSS/JS и PHP обработчик, `/var/www/sy3.ru`; Git отсутствует |
| `it-business-partner.ru` | React/Hono приложение, `/var/www/IT-business-partner.ru`; Node на порту 3000; есть staged/dirty/untracked и неопубликованные материалы |
| Веб-сервер | `/etc/nginx/sites-enabled/sy3.ru.conf`, `/etc/nginx/sites-enabled/it-business-partner.ru.conf` |
| Источник новой версии | ветка `codex/wordpress-sy3-20261022` репозитория `suyazov/IT-business-partner.ru`, подкаталог `wordpress/` |

Старый рабочий каталог личного сайта не является чистым checkout опубликованного Git. Его нельзя reset/clean, заменять clone или объявлять восстанавливаемым по удалённому репозиторию. Секретные файлы не входят в новый source diff и в публичные артефакты.

## Объём отдельного разрешения

Переключить `sy3.ru` и `it-business-partner.ru` на две отдельные установки WordPress; создать для них отдельные рабочие базы/пользователей MariaDB; подготовить доступ PHP-FPM и изменить только конфигурации этих двух доменов с проверкой Nginx и reload. Сертификаты, DNS, почта, сторонние сайты и платные API не входят в scope. Общую конфигурацию PHP менять только при доказанной необходимости и точном согласовании.

Предложенные точные новые каталоги: `/var/www/sy3-wordpress` и `/var/www/itbp-wordpress`. Предложенные отдельные схемы MariaDB: `sy3_wp_20261022` и `itbp_wp_20261022`; перед созданием проверить отсутствие одноимённых используемых ресурсов. PHP обрабатывать через существующий socket `/var/run/php-fpm-sy3-ru.sock` от `php-sy3`, сначала проверить работу в новых каталогах. Изменение общей PHP-конфигурации и создание новых системных пользователей не входят в предложение.

Секреты — только в `/root/.config/client-access/<domain>/wordpress.env`, каталог `0700`, файл `0600`, вне Git; в `wp-config.php` секреты не выводить в команды/логи. Не переиспользовать локальные preview-пароли на production.

## Порядок после разрешения

1. Зафиксировать точный reviewed commit; проверить required checks и независимое review перед routine merge. Эта ветка не имеет права обходить review.
2. Получить общие project locks двух сайтов и lock изменения общей Nginx-конфигурации. Проверить активных writers. Для создания/очистки backup получить общий storage lock; чужой занятый lock не снимать.
3. Защитить невосстановимое исходное состояние: точный статический сайт sy3.ru, обе текущие конфигурации доменов и необходимые source/runtime-данные личного сайта. Хранить вне webroot, с manifest, хешами, restore procedure, coverage и `delete_after` не позже семи дней. Существующие dirty/unpushed изменения, секреты и evidence не удалять. Полный архив сервера не нужен.
4. Развернуть две новые WordPress-установки в новых каталогах с отдельными базами MariaDB. На этом этапе домены всё ещё обслуживаются прежними приложениями. На новых установках запретить индексацию до переключения.
5. Импортировать контент именно на новых установках, с их конечными URL. Проверить домашние URL, отсутствие loopback-адресов и правильный `SY3_MAIN_URL=https://sy3.ru` у личного сайта. Не копировать SQLite в боевую MariaDB: контент воспроизводится импортом, а новые редакторские изменения переносятся отдельным штатным экспортом.
6. Подготовить PHP-FPM обработку обеих установок через указанный существующий пул с минимально нужными правами, без изменения пулов. Проверить через отдельный loopback/Host-сценарий; если нужна правка общего PHP runtime, остановиться на этом отдельном расширении scope.
7. Сохранить обработку старых публичных ассетов личного сайта: точные `/images/` и `/videos/` направить к существующему `dist/public` или перенести только нужные файлы в новую установку с проверкой. Старое Node-приложение не останавливать до подтверждённой замены API/маршрутов и live-проверки. Старый PHP обработчик sy3.ru не переносить как неиспользуемую форму.
8. Изменить только два доменных vhost, сохранить TLS и существующие защитные include, выполнить `nginx -t` и reload только при успехе. Для WordPress: `try_files $uri $uri/ /index.php?$args`, существующие PHP-файлы через согласованный FPM; запретить исполнение PHP в uploads и доступ к конфигам/скрытым файлам.
9. Проверить живые страницы и конечные ассеты, старые адреса, sitemap, llms.txt, sales feed, Telegram/email/телефон. Убедиться, что production не содержит preview noindex; разрешить индексацию только после успешных проверок. Обновить Context фактическими URL и commit.
10. Сохранить rollback до подтверждения восстановления исходного состояния из независимого источника. Проверить сроки и очистить только доказанные временные дубли. Зафиксировать результат очистки или причину и дату удержания.

## Сохранение адресов

Основной сайт:

| Старый адрес | Новый адрес |
| --- | --- |
| `/index.html` | `/` (301) |
| `/services.html` | `/services/` (301) |
| `/bitrix24.html` | `/services/bitrix24/` (301) |
| `/portfolio.html` | `/cases/` (301) |
| `/about.html` | `/about/` (301) |
| `/contact.html` | `/contacts/` (301) |

Личный сайт:

- `/portfolio` → действующая страница подборки.
- Старые `/portfolio/<slug>`, совпадающие с разрешёнными кейсами AFFiNE, → 301 на соответствующие `/cases/.../` основного сайта, только после его готовности. VIP26 не входит в каталог Share; его прежний материал сохранён в исходниках и локальном черновике.
- `/blog` остаётся страницей архива; три старые статьи сохранены в исходниках и локальных черновиках до редакторской проверки. Ссылка на пустой архив убрана из меню. Перед переключением согласовать судьбу старых адресов статей; не считать их перенесёнными публичными страницами.
- `/sitemap.xml` → `/wp-sitemap.xml` (301); `/llms.txt` и `/sales/portfolio-feed.json` обслуживаются WordPress.
- Старые `/images/` и `/videos/` должны остаться доступны при смене корня. Legacy API не используется новой темой; отключение старого сервиса — отдельный шаг после проверки его использования.

## Восстановление

До live-проверки исходные каталоги и Node-процесс сохраняются. При неуспехе вернуть ровно две исходные vhost-конфигурации из manifest, выполнить `nginx -t`, reload и проверить исходные сайты. Новые базы и каталоги не удалять автоматически: изолировать и зафиксировать состояние. Восстановление нельзя объявлять проверенным до фактического read-back.
