## План и выполнение

`build-editorial-transfer.py` читает полные версии и поля из точных Git blobs, сверяет исходный baseline SHA и каждый body hash. Intent создаётся только вне webroot, без перезаписи существующего файла. В текущей задаче приватный каталог — `/root/preview/sy3-wordpress-20261022/private/editorial-refactor-20261023/`; существующий `runtime-baseline.json` сохраняется для проверки конфликтов и восстановления разрешённых полей, новая резервная копия не создаётся.

`transfer-editorial.php` работает через WP-CLI в трёх режимах:

- `plan` — только чтение production. Проверяет type/slug, исходные тела и поля всех360 объектов, alt/URL/подписи/байты37 вложений, соответствие311 body hashes вспомогательному JSON и действующий quality gate. Фиксирует fingerprints всех полей и metadata397 записей, options, intent и самого updater. Конфликт останавливает весь план.
- `exercise` — только существующий изолированный preview. Сопоставляет уникальные type/slug и изображения по фактическим SHA, применяет SQL в транзакции, проверяет ожидаемые строки и защищённые поля, затем всегда выполняет ROLLBACK и проверяет исходное состояние. Production IDs этим сопоставлением не заменяются.
- `apply` — только точный production `https://sy3.ru/`, expertise, HTTPS. Требует отдельного точного разрешения, SHA утверждённого плана и PID держателя двух project locks. Проверяет scoped `sy3-wordpress-content.lock`, InnoDB и advisory lock издателя; повторяет все fingerprints под row locks перед первой записью. Прямой SQL сохраняет даты и исключает save/transition hooks, почту, ботов и публикацию.

Apply меняет только отдельную базу sy3 и один project-only JSON; общей storage-операции здесь нет. Поэтому чужой `bridge-sy9-storage-mutation.lock` не блокирует контентный перенос. Этот глобальный lock по регламенту11 остаётся обязательным для отдельной очистки накопленных дублей и временных файлов. При ошибке незавершённый staging-файл удаляется только с получением глобального lock; иначе его точный путь и срок удержания выводятся в ошибку для cleanup receipt.

Переменные оператора: `SY3_EDITORIAL_TRANSFER_MODE`, `SY3_EDITORIAL_INTENT`, `SY3_EDITORIAL_TRANSFER_PLAN`, `SY3_EDITORIAL_APPROVED_PLAN_SHA256`, `SY3_EDITORIAL_PROJECT_LOCK_PID`; для apply дополнительно `SY3_ALLOW_PRODUCTION_IMPORT=1`. Сами переменные не заменяют разрешение владельца. Пути plan/intent должны вести к файлам root:root0600 непосредственно в указанном приватном каталоге. После изменения updater план необходимо пересоздать и проверить заново.

При apply файл JSON готовится с сохранением владельца/прав и переключается атомарно перед COMMIT. Пока транзакция не завершена, несовпадение body guard допускает временный fallback; успешный read-back подтверждает совместное новое состояние. До COMMIT ошибка вызывает ROLLBACK и восстановление прежнего JSON из проверенного Git blob; отдельного файла backup нет. После COMMIT очищается только post/meta cache затронутых IDs этого WordPress.

При аварийном завершении после rename и до COMMIT возможен точный `DB_BEFORE_FILE_AFTER`: база откатилась, файл новый. Этот вариант распознаётся тем же неизменяемым планом и hashes. Повторный apply с той же authority заново получает все locks, проверяет исходные SQL fingerprints и options под row locks, применяет разрешённые поля, сохраняет уже правильный JSON и завершает COMMIT. Неизвестные смешанные состояния блокируются, без затирания ручных правок. `DB_AFTER_FILE_AFTER` означает уже завершённый перенос, запись не повторяется.

Повторный apply точного уже применённого плана — `ALREADY_APPLIED`, без записи. Любое другое состояние — конфликт. Если после COMMIT обнаружено расхождение, автоматического затирания чужих правок нет: сохранить receipt и сравнить затронутые поля с планом. Для восстановления использовать исходные body/title/excerpt/description из существующего baseline, прежние alt из принятого manifest и JSON из Git `a74fcd23af7f75ba784020b5067ddfa652a7ed50`. Новые description для4/5/6/8 восстановить именно удалением созданных строк, а не записью пустых значений. Обратное изменение допустимо только при совпадении текущего поля с нашим after; конфликтующее поле сохранить и вынести на разбор. Это отдельная точная операция, не скрытый повтор импорта.
