# Заявки с сайта в SY3 Support

Форма располагается перед подвалом на главной, странице контактов, услугах и остальных публичных страницах sy3.ru. Кнопки «Обсудить задачу» ведут к ней. Личный сайт и редакционные тексты не меняются. В WordPress появляется закрытый раздел **Заявки с сайта** для администраторов.

Обязательны телефон или email и согласие. Имя и описание задачи необязательны. Сохраняются также страница, время и пять стандартных UTM-меток; получатели и адреса API из запроса посетителя никогда не принимаются. Обращение получает устойчивый номер `SY3-…`. Повтор одного запроса возвращает тот же номер.

## Защита формы

Эталон — принятый LEMESH PRO `ad651ed420283a8ee3407a11ac5cfb0250ce2a5c`, `inc/integrations/leads.php`. Перенесены honeypot, WordPress nonce, HMAC-токен на 12 часов, защита от повторной отправки и ограничение пяти заявок с IP за десять минут. Свежий токен выдаёт некешируемый endpoint; без JavaScript открывается отдельная некешируемая форма. Поля проверяются до расходования токена и лимита. Непустой honeypot, включая строку `0`, не создаёт заявку.

Счётчик имеет фиксированное окно; сырые IP в заявку и счётчик не записываются, используется HMAC. Применяется только серверный `REMOTE_ADDR`, а не заголовок, заданный посетителем. Неблокирующие `flock` и 256 полос для каждого класса блокировок защищают от гонок и неограниченного создания lock-файлов отклонённым спамом. Переводы строк нормализуются, недопустимые типы/символы/URL отклоняются. Подтверждение сохранения следует после `fsync` файла, атомарного `rename` и `fsync` каталога.

## Доставка и границы доступа

WordPress пишет JSON-заявку вне webroot в `/var/lib/sy3-wordpress/leads/queue`. Файлы `0600`, пользователь `php-sy3`. Публичных API просмотра заявок нет. Токены ботов не копируются в WordPress, базу, uploads или репозиторий.

Отдельный root-отправитель `/usr/local/lib/sy3-leads/dispatcher.py` читает только данные, не исполняет PHP или код сайта. Root-only конфигурация `/root/.config/client-access/sy3.ru/lead-delivery.json` содержит проверенные личные назначения Telegram/MAX. Источники токенов — существующие canonical файлы SY3 Support; дополнительный CA MAX сохраняет полноценную проверку TLS. Bot runtime, webhook, проекты и SQLite ботов не меняются. Заявка не становится заданием Bridge.

У каналов отдельные состояния. Подтверждённый канал не отправляется повторно из-за сбоя другого. Явный HTTP429 откладывается; тайм-аут, неизвестный результат или прерванная отправка требуют проверки личного диалога, чтобы не создавать дубли. Полное отсутствие дублей после неизвестного внешнего результата не обещается: API не предоставляет общей транзакции с локальной очередью. Администратор видит понятные статусы каждого канала. Сообщения не используют HTML/Markdown и не превышают ограничения платформ.

Root-owned `state/` хранит только состояние/отпечаток и подтверждение доставки; группа WordPress имеет чтение. Рабочий lock, запись состояния и переименование синхронизируются на диске. Системная служба получает запись только в `state/`, read-only остальной файловой системы и необходимые ограничения. Один запуск ограничен 20 обращениями / 75 секундами, MAX — не чаще двух сообщений в секунду. Журнал содержит счётчики и безопасные коды, без контактов, получателей и токенов.

## Проверка и включение

```sh
python3 -m unittest discover -s wordpress/delivery -p test_dispatcher.py
SY3_LEADS_STORAGE=/root/preview/sy3-wordpress-20261022/private/leads-preview wp --path=/root/preview/sy3-wordpress-20261022/public --allow-root eval-file wordpress/tools/check-leads.php
systemd-analyze verify wordpress/deploy/systemd/sy3-leads.service wordpress/deploy/systemd/sy3-leads.timer
git diff --check
```

PHP-проверка допускает только известный локальный preview, создаёт собственные помеченные fixtures, очищает их и запрещает HTTP/mail. Python-тесты не используют реальные доступы или сеть. Browser/native/concurrency receipts размещаются в private каталоге задачи.

Установка новых ресурсов и включение двух systemd unit требуют точного разрешения владельца по AGENTS.md. До разрешения production не изменяется. После независимого review точного commit и разрешения оператор устанавливает только согласованные файлы; `install-lead-delivery.py` проверяет чистый exact head и владельца обоих project locks через `SY3_LEADS_REVIEWED_HEAD` / `SY3_LEADS_LOCK_PID`, под флагом `SY3_LEADS_ALLOW_PRODUCTION=1`. Helper не включает таймер самостоятельно.

Затем публикуются плагин/два theme hooks, обновляется строго прежняя собственная privacy-страница с guard содержимого, заголовка и анонса; включается только `sy3-leads.timer`. Боевой canary — одна явно тестовая заявка владельцу, проверка обоих подтверждений, honeypot и повтора. Все прежние статьи, обложки, даты и редакционные очереди сравниваются до/после. Текст, условия и назначение реального хранения заявок описывает страница `/privacy/`; тестовые jobs и operational receipts не удалять как мусор без проверки назначения.

Код до изменения восстанавливается из принятого Git; проверенная исходная privacy-страница совпадает с прежним `content/pages.php`. Новые резервные копии этой задачей не создаются. Отключение таймера останавливает будущую доставку, сохраняя заявки и подтверждения.
