# Единый справочник сотрудников: почему ФИО недостаточно для автоматизации

## Человек, учётная запись и назначение — не одно и то же

Справочник сотрудников часто начинают с имени и должности. Для списка этого достаточно, для автоматизации — нет. Один человек может иметь несколько учётных записей в разных системах. Он способен работать в нескольких подразделениях, менять роль и возвращаться к сотрудничеству позднее. Если каждый случай создаёт независимого человека, история распадается. Если всё хранится одним текущим полем, прошлые назначения исчезают.

Полезно разделить устойчивую запись человека, внешние аккаунты и рабочие назначения. Аккаунт отвечает за вход в конкретную систему. Назначение описывает роль, подразделение и период. Человек связывает необходимые рабочие события в допустимой области. Такая модель помогает не выводить кадровый смысл из случайного имени пользователя или адреса почты.

Точный набор сведений определяет организация с ответственными специалистами. Не нужно превращать операционный справочник в полный кадровый архив. Для назначения задачи может быть достаточно идентификатора, имени и доступной роли. Избыточные личные сведения усложняют доступ без полезного влияния на процесс.

## Карта сущностей сотрудника

| Сущность | Что описывает | Какие связи нужны | Ошибка при смешении |
| --- | --- | --- | --- |
| Человек | Устойчивого участника | Необходимые рабочие события | Смена фамилии создаёт новую историю |
| Аккаунт | Вход в определённый сервис | Человек и область сервиса | Один общий логин скрывает исполнителей |
| Назначение | Роль и подразделение во времени | Человек, период, область | Текущее поле переписывает прошлое |
| Разрешение | Допустимые действия | Роль и конкретная область | Должность автоматически даёт всё |
| Внешнее соответствие | ID в другой системе | Источник и локальная запись | Импорт сопоставляет по ФИО |
| Статус участия | Текущее рабочее состояние | Порядок доступа и назначения задач | Архив удаляется вместе с доступом |
| История изменения | Принятые значимые переходы | Автор и основание | Нельзя объяснить прежний результат |

Не обязательно внедрять отдельную большую платформу ради такого разделения. Иногда достаточно нескольких связанных справочников в существующей системе. Но смысл должен быть явным. Иначе последующая интеграция столкнётся с тем, что одна строка одновременно означает человека, его рабочее место и привилегии.

## Почему ФИО не подходит для сопоставления

Два сотрудника могут иметь одинаковые имена. Написание может различаться сокращением, раскладкой или опечаткой. Фамилия меняется, а некоторые источники содержат только инициалы. Автоматическое объединение по такому тексту способно прикрепить задачи или показатели не к тому человеку. Отсутствие совпадения, наоборот, создаст лишнего дубля.

Устойчивый идентификатор отделяет связь от подписи. Для внешнего обмена сохраняют пару «источник — внешний ID», потому что одинаковые числа разных сервисов не обязательно означают одного участника. При неясном соответствии создают задачу проверки. Нельзя выбирать ближайшее имя без основания только ради полного импорта.

Первичный технический пример — [SCIM Core Schema, RFC 7643](https://datatracker.ietf.org/doc/html/rfc7643). В схеме управления идентичностями выделены идентификаторы ресурсов и пользовательские атрибуты. Это ориентир для обсуждения устойчивых связей, а не требование применять SCIM в любой внутренней программе. Конкретный контракт определяют по существующим источникам.

## Диагностический пример двух тёзок

В учебном наборе есть два человека с одинаковыми ФИО в разных подразделениях. Один получает задачу, другой участвует в расчётном показателе. Импорт должен связать события по подтверждённым идентификаторам, а не по отображаемому имени. После загрузки проверяют обе истории, чтобы обнаружить не только потерянную запись, но и ошибочно прикреплённую.

Затем у первого сотрудника меняют фамилию. Его прежние задачи и назначения должны оставаться объяснимыми в рамках принятой модели. Новое имя не создаёт автоматически нового человека. Историческое представление может требовать сведения на момент события, а оперативный список — текущую подпись. Эти задачи различаются и должны быть согласованы.

Третий вариант — старый внешний аккаунт закрыт, создан новый. Нужно установить допустимую связь с человеком и не переносить права автоматически по похожему имени. Снятие прежнего доступа и сохранение рабочей истории — разные операции. Их смешение приводит либо к потере полезных данных, либо к лишним полномочиям.

| Ситуация в тесте | Идентичность человека | Аккаунт | Назначение | Что проверяется |
| --- | --- | --- | --- | --- |
| Два одинаковых имени | Два разных ID | Раздельные | Разные области | Нет ложного объединения |
| Смена фамилии | Прежний ID | По принятому порядку | История сохраняется | Подпись не разрушает связи |
| Новый сервис | Та же подтверждённая связь | Новый внешний ID | Нужная роль | Нет совпадения по одному номеру |
| Перевод | Человек прежний | Доступ пересмотрен | Новый период | Прошлое не переписано |
| Завершение участия | История остаётся по политике | Доступ ограничен | Назначение закрыто | Нет случайного удаления событий |

## Периоды назначений

Роль и подразделение могут действовать с определённой даты. Для отчёта прошлого месяца нельзя автоматически использовать текущее назначение. Нужно понимать, к какой области относилось событие и какие правила применялись. Это особенно важно для показателей, распределения ответственности и маршрутов согласования.

Если человек совмещает несколько ролей, одного поля «должность» недостаточно. У каждого назначения есть область и условия. Система выбирает полномочие для конкретной операции, не суммируя всё без ограничений. Руководитель филиала не обязательно видит другую компанию только потому, что у него есть ещё одна техническая роль.

Изменение даты назначения может затронуть уже принятые расчёты или задачи. Поэтому его влияние оценивают отдельно. Исправление исходной ошибки и новый перевод — разные причины. История должна позволять понять, почему изменился результат, а не просто показывать последнюю аккуратную строку.

## Бизнес-процесс синхронизации справочника

Вход — принятые сведения из назначенного источника. Система определяет внешний идентификатор, ищет известное соответствие и проверяет область. Однозначные изменения применяются к своим полям. Новые или спорные записи поступают ответственному. После решения обновляются нужные назначения и доступы по отдельной политике.

Владелец справочника отвечает за качество идентичностей. Руководитель процесса — за смысл назначения. Администратор доступа — за технические полномочия. Разработчик обеспечивает сопоставление и историю. Если эти функции совмещены, решения всё равно полезно различать: исправление имени не обязано менять разрешения, а прекращение доступа не должно стирать авторство прошлых событий.

Выход — согласованный набор людей, аккаунтов и ролей, пригодный для текущей работы и объяснения истории. Если источник неполон, состояние показывается явно. Неизвестный внешний ID нельзя автоматически прикрепить к первому подходящему имени. Лучше управляемый разбор, чем тихое распространение ошибочной связи во все процессы.

## Слияние и разделение дублей

Перед объединением смотрят связанные задачи, документы, показатели и внешние соответствия. Подозрение на дубль не является доказательством. Решение должно иметь основание и принимающую роль. Если записи объединяются, необходимо сохранить полезную историю и не расширить доступ за счёт автоматического суммирования всех старых разрешений.

Обратный случай — ошибочно объединённые люди. Разделение потребует определить принадлежность каждого события. Не все данные удастся распределить автоматически. Поэтому первоначальные связи и след изменений имеют практическую ценность. Быстрое удаление одной строки может скрыть дефект, но сделать восстановление гораздо сложнее.

Массовая нормализация имён также не должна менять идентичность. Исправление регистра или пробелов — техническое преобразование отображения. Установление, что два источника относятся к одному человеку, — содержательное решение. Их различают в плане и отчёте, чтобы не выдавать очистку текста за полноценное качество справочника.

## Доступ к персональным и рабочим данным

Операционная роль получает только нужные сведения. Участнику проекта может быть виден исполнитель задачи, но не весь профиль человека. Экспорт, поиск и уведомления требуют той же оценки состава. Закрытое подробное поле не защищает данные, если они включены в общую подпись записи.

Технической поддержке для ошибки сопоставления часто достаточно безопасных идентификаторов и обезличенного примера. Нет необходимости копировать кадровые документы в общий репозиторий. Права на исходный источник и подробности выдаются по установленному процессу. Доступность данных в одном сервисе не означает право распространять их всем подключённым инструментам.

При завершении участия проверяют действующие сессии, назначения и автоматические действия. Конкретный порядок зависит от платформы и политики. Важно, чтобы новые операции соответствовали актуальным полномочиям, а полезная история оставалась в принятой области хранения. Одно удаление аккаунта не решает обе задачи автоматически.

## Матрица приёмки единого справочника

| Сценарий | Подготовленное условие | Критерий результата | Доказательство |

| Тёзки | Одинаковые ФИО, разные ID | События не смешаны | Две независимые истории |

## Комплект для сопровождения

Нужны модель сущностей, карта владельцев полей, правила внешнего сопоставления и процедура спорных случаев. Для каждого существенного назначения определяют период и область. Для тестов сохраняют обезличенных тёзок, смену имени и перевод. Такой набор показывает реальные свойства автоматизации лучше единственного идеально заполненного профиля.

Полезные показатели — несопоставленные внешние записи, ошибочные объединения и доля назначений с понятным периодом. Само отсутствие дублей на экране не доказывает корректность: ошибочно слитые люди тоже выглядят одной строкой. Качество определяется устойчивой связью между человеком, его рабочей ролью и событием. На этой основе можно надёжнее строить согласования, расписание и управленческие расчёты.
