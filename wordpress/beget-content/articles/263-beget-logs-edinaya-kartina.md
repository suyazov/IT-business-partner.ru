# Единый журнал сайта и интеграций: какие события собирать

Если заявка проходит сайт, очередь и CRM, её история распределяется между несколькими приложениями. При сбое команда открывает разные журналы и пытается угадать, какие строки относятся к одному событию. Централизованный сбор помогает увидеть общую картину, но сам по себе не создаёт связь между операциями. Сначала нужно договориться, что записывают приложения, как они обозначают состояния и по какому признаку сопоставляют один бизнесовый маршрут.

Beget описывает один из вариантов сбора журналов с помощью Vector в серверном окружении. Сам Vector предоставляет компоненты получения, преобразования и направления событий. Возможности выбранной конфигурации проверяются по актуальной документации. Ниже — наша схема проектирования журнала для сайта и интеграций: какие факты нужны поддержке, как не собирать лишние данные и как принять полезный результат, а не только работающий сборщик.

## Начинаем с вопросов, на которые должен ответить журнал

Хороший журнал помогает установить, было ли событие принято, какой участок начал обработку, что вернула следующая система и чем закончилось дело. Для заявки это путь до доступной менеджеру карточки. Для обновления каталога — применение конкретного изменения. Для фонового задания — понятный итог попытки. Записывать все доступные данные без этих вопросов означает накапливать объём, в котором всё равно трудно найти причину.

Уточните, кто использует записи и какие решения принимает. Разработчик ищет место ошибки, интегратор сопоставляет системы, владелец процесса уточняет последствия для клиентов. Им нужны разные представления одного эпизода. В общий отчёт не обязательно включать технические подробности каждого шага, однако сведения должны позволять ответственному перейти от симптома к проверяемому объекту и следующему действию.

Не путайте журнал событий с полной базой бизнесовых данных. У него другая задача и другой жизненный цикл. Чтобы понять, что заявка дошла до CRM, обычно достаточно безопасного идентификатора и результата перехода. Копия всей переписки, телефона и содержимого формы может оказаться лишней. Состав данных согласуют по конкретным задачам диагностики и принятому порядку доступа, а не по принципу «потом когда-нибудь пригодится».

## Общий словарь состояний

Одинаковые слова в разных приложениях могут обозначать разные вещи. Сайт записал «успех», потому что поставил задачу в очередь; обработчик — потому что отправил запрос; CRM — потому что создала объект. Все три факта полезны, но не взаимозаменяемы. Для поддержки нужно различать принятие, попытку исполнения и подтверждённый деловой результат. Иначе зелёные сообщения каждого компонента будут скрывать разрыв между ними.

| Состояние | Что реально произошло | Чего ещё не знаем | Полезное подтверждение |
| --- | --- | --- | --- |
| Принято | Входное событие зарегистрировано | Будет ли оно успешно обработано | ID события и источник |
| Назначено | Исполнитель получил работу | Завершится ли внешнее действие | ID задания и попытки |
| Отправлено | Сделана передача следующему участнику | Применены ли данные получателем | Тип вызова и связанный запрос |
| Подтверждено | Получен ожидаемый ответ | Достаточен ли ответ для делового итога | Код результата и ссылка по ID |
| Завершено | Выполнен согласованный критерий операции | Есть ли последствия других ошибок | Состояние целевого объекта |
| Требует разбора | Автоматическое продолжение ограничено | Какое решение примет владелец | Причина и назначенный следующий шаг |

Названия могут быть другими, если они согласованы и однозначны. Важнее смысл переходов и владельцы фактов. Если внешний сервис отвечает лишь о принятии задачи, нельзя автоматически обозначать операцию как завершённую. Для такого маршрута описывают дальнейшее подтверждение либо честно ограничивают утверждение журнала. Уровень уверенности должен соответствовать тому, что действительно наблюдалось.

Отдельно определите повторы. Одно бизнесовое событие способно вызвать несколько технических попыток. Если все они имеют один неразличимый номер, сложно понять последовательность; если каждая теряет связь с исходной операцией, трудно обнаружить дубль. Поэтому полезно разделять идентификатор деловой операции и идентификатор попытки. Конкретный формат выбирают по архитектуре, сохраняя возможность безопасного сопоставления.

## Минимальная структура записи

| Поле | Назначение | Пример безопасного смысла | Ошибка проектирования |
| --- | --- | --- | --- |
| Время | Поставить событие на общую линию | Время с понятной зоной | Сравнивать разные зоны как одну |
| Компонент и среда | Найти владельца факта | Обработчик рабочей или тестовой среды | Не отличать тест от production |
| Тип события | Понять действие | Принятие заявки или результат передачи | Свободный текст без устойчивой категории |
| Ключ операции | Связать переходы систем | Безопасный внутренний идентификатор | Использовать телефон клиента как ключ |
| Попытка | Разделить исполнения | Номер или отдельный ID | Терять связь повтора с исходным событием |
| Этап и результат | Зафиксировать известное состояние | Принято, завершено, нужен разбор | Объявлять отправку деловым успехом |
| Причина ограничения | Назначить дальнейшую работу | Тип отказа без секретных деталей | Записывать только общее слово ошибка |
| Версия приложения | Связать эпизод с поставкой | Принятая версия компонента | Искать проблему в коде, который не работал |

Ниже условный пример структуры, а не запись нашего клиента. Поля и значения подобраны для объяснения метода; они не являются готовой конфигурацией Vector и не включают личные сведения.

```json
{
  "occurred_at": "2026-10-23T09:00:00+03:00",
  "component": "crm-delivery-worker",
  "environment": "test",
  "event_type": "delivery.attempt.finished",
  "operation_id": "example-operation-17",
  "attempt": 2,
  "stage": "receiver_accepted",
  "result": "pending_confirmation",
  "application_version": "example-release"
}
```

В этом примере получатель принял событие, но окончательное подтверждение ещё ожидается. Такая запись полезнее безусловного «успешно», потому что объясняет текущую границу. Идентификатор операции служит для сопоставления и не является доказательством права доступа. Если программа принимает внешнюю метку, правила её проверки и связывания определяются приложением; одна произвольная строка не должна подменять авторизацию или достоверность события.

## Как связать сайт, очередь и CRM

Начните с одной контрольной операции и пройдите весь путь. Где появился первый ID, как он сохраняется в очереди, каким образом сопоставляется с объектом CRM? Иногда системы используют разные ключи. Тогда нужна проверяемая связь между ними, а не требование, чтобы все компоненты называли объект одинаково. Аналитик описывает эту связь, а технический исполнитель обеспечивает её сохранение в нужных точках.

Время помогает найти эпизод, но редко даёт достаточную уникальность. За одну секунду несколько посетителей могут отправить формы, а одна задача — выполнить повтор. Сопоставление только по близким временным отметкам создаёт риск принять чужую строку за нужную. Поэтому временной интервал используется вместе с типом события и безопасными ключами. Если связи нет, это отдельный разрыв наблюдаемости, который нужно устранить в проекте.

Не создавайте ложную точность, когда компонент не отдаёт нужного подтверждения. Можно честно записать «передано, итог неизвестен» и назначить проверку по целевой системе. Такой статус помогает безопасно продолжить разбор. Самостоятельно считать отсутствие ошибки доказательством завершения опаснее для процесса, потому что после сбоя команда не понимает, какие операции уже состоялись и какие допустимо повторять.

## Сборщик и хранилище принимаются отдельно

После согласования событий выбирают подходящий маршрут сбора. В Vector источники, преобразования и получатели данных образуют конфигурацию конкретного проекта. Не требуется автоматически включать все контейнеры и все файлы на сервере. Сначала устанавливают нужные источники и состав полей, затем проверяют получение и направление данных в разрешённое место. Права сборщика должны соответствовать его реальной задаче.

Наличие процесса сборщика не подтверждает, что запись дошла до выбранного хранилища. Для приёмки нужны контрольное событие, наблюдение его прохождения и возможность найти его там, где работает поддержка. Отдельно проверяют, что происходит при недоступности получателя и росте объёма. Конкретные гарантии доставки зависят от компонентов и настроек; их нельзя объявлять одинаковыми для любого готового примера из инструкции.

Если преобразование удаляет лишние поля, проверьте это на разрешённой тестовой записи. Необходимо подтвердить и сохранение нужного диагностического контекста, и отсутствие лишнего содержимого. Удобно иметь небольшой набор сценариев: нормальное событие, понятный отказ и запись с полем, которое не должно попадать дальше. Проверка выполняется без настоящих секретов, чтобы сама приёмка не создала проблему хранения.

## Доступ, сроки и стоимость наблюдения

У общего журнала есть пользователи, срок хранения и ответственный за изменение схемы. Специалисту поддержки может быть нужен доступ к техническим состояниям без полного содержимого клиентских данных. Аналитику — агрегированная картина без сырого текста сообщений. Разграничение обсуждают вместе с владельцем процесса и техническим исполнителем. Сам факт объединения источников не означает, что все участники должны видеть весь собранный массив.

Объём событий нужно измерять до обещания постоянного хранения всего подряд. Частый подробный журнал способен расходовать заметные ресурсы и скрывать важные сообщения в шуме. Решение о детализации связывают с вопросами поддержки, обычным режимом и ограниченной диагностикой. Если на время инцидента включён дополнительный сбор, у него должны быть назначение, ответственный и момент пересмотра. После завершения состояние фиксируют в актуальном паспорте.

Сроки хранения определяются потребностью проекта и действующими требованиями, которые владелец рассматривает отдельно. Универсальное число дней не подходит всем процессам. Нужно учитывать, когда обнаруживаются ошибки и какой интервал требуется для сопоставления с внешними системами. При этом журнал не должен бессрочно превращаться в незаявленную копию бизнесовой базы. Техническая реализация ротации и очистки следует согласованной политике, а не случайному размеру диска.

## Какие проверки делают журнал полезным

| Сценарий | Проверяемая способность | Что предъявляется | Условие неполной приёмки |
| --- | --- | --- | --- |
| Нормальная операция | Проследить путь до результата | Связанные события нескольких компонентов | Есть только факт отправки |
| Повторная попытка | Разделить повтор и новую работу | Один деловой ключ и разные попытки | Все записи выглядят независимыми |
| Отказ получателя | Найти причину и следующий шаг | Понятное состояние и владелец разбора | В журнале лишь общий текст ошибки |
| Недоступное хранилище | Понять поведение сбора | Результат согласованной проверки доставки | Работающий агент принят за гарантию сохранности |
| Ограниченные поля | Не передавать лишнее | Безопасная тестовая запись после обработки | В хранилище появились запрещённые сведения |
| Смена версии | Связать событие с поставкой | Версия работающего компонента | Анализируется другой исходный код |

После внедрения проведите разбор одного реального разрешённого вопроса поддержки или заранее согласованного теста. Новый участник должен найти операцию и объяснить, на каком переходе она находится. Если для этого всё ещё нужны личные пояснения автора программы, журнал пока не обеспечивает самостоятельной диагностики. Это не повод собирать больше строк: возможно, не хватает одного устойчивого ключа или понятного словаря состояний.

## С чего начать проект наблюдаемости

Мы начинаем с критичного бизнесового маршрута и короткой карты систем. Вместе с разработчиком и интегратором определяем необходимые события, связи, ограничения и способ приёмки. После этого выбирается инструмент сбора, а при необходимости подключается профильный специалист по инфраструктуре или данным. Такой порядок позволяет оценить полезность журнала по реальным задачам команды, не обещая, что установка одного сервиса автоматически решит все инциденты.

Для обсуждения достаточно назвать процесс, его участников и типичную проблему: пропавшая заявка, зависшее обновление или неизвестный итог передачи. Исходные доступы и журналы передаются только после согласования объёма в защищённом контуре. Результатом этапа становятся рабочая схема событий, проверяемая связность операции и понятные артефакты для дальнейшей поддержки.
